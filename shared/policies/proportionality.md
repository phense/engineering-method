# Proportionality

Apply this execution rule within every selected skill. It does not select a
lifecycle, introduce a controller, or waive correctness requirements.

- Match effort to the actual change, its reversibility and concrete failure
  risks. Reusing existing skills normally calls for trigger, consistency,
  installation and attribution checks; it does not itself justify architecture
  machinery or a new evaluation framework.
- Start with the smallest sufficient evidence: inspection and focused local
  checks. Before a paid model evaluation, name the unresolved question, why
  existing evidence cannot answer it, and the bounded scope of the run.
- Reuse evidence when its relevant inputs and assumptions are unchanged. Record
  the checked revision, affected paths and limits. A harness/parser correction
  normally needs a local regression or retained-transcript replay, not a fresh
  complete host matrix. Never describe replay as a fresh live execution.
- Default to one independent review where risk requires it, followed by focused
  checks of fixes. Another complete review requires a new material risk or
  changed integration boundary. Mechanical work stays with the coordinator.
- Delegate only when the independent task saves meaningful time or supplies
  necessary expertise. Prefer concise briefs and reports; do not add agents,
  stronger models or parallel runs merely because they are available.
- Respect the user's subscription, effort permissions and stated time or usage
  limits. Do not infer available quota or cost when telemetry is unavailable.
  A quota reset does not expand the authorized effort budget.

## Effort brake

Before another expensive run or review round, reassess if two attempts have not
resolved the same question, verification tooling is becoming more work than the
requested change, or effort materially exceeds the initial scope. Stop further
expensive dispatch, checkpoint completed work and open findings, and recommend
the cheapest defensible completion path. Continue useful bounded local work.
If that path needs materially more paid execution, explain its expected benefit
and obtain approval before proceeding. Do not ask the user to choose a method.

This is a pause/re-scope rule, not a success condition. Preserve unresolved
findings and distinguish product defects from evidence-tool defects. Never make
a failing gate pass by weakening its assertions, hide missing evidence, or mark
unfinished work complete. Explicit user requirements take precedence; surface
any acceptance change needed for a cheaper completion path.
